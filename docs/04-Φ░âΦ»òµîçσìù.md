# 04 · 调试指南

按**你看到的症状**查，不按模块查。

## 通用调试三板斧

```bash
# 1. 不花钱先看检索对不对
python huijian.py search TERM --also ...

# 2. 看会发出哪些请求
python huijian.py run TERM --dry-run

# 3. 逐条看模型返回和拦截
python huijian.py run TERM -o out/ --limit 3 --debug
```

**遇到任何问题，先跑这三条。** 大部分故障在第一条就暴露了。

---

## 症状：检索结果是 0

```
共 0 段
```

**先确认语料在**：

```bash
ls corpus/ | head
python3 -c "import pathlib; print(len(list(pathlib.Path('corpus').rglob('*.txt'))))"
```

应该有 20 多个书名目录、3000 多个 txt。如果没有，`fetch` 没跑成功。

**再确认检索词的字形**。语料是繁简混杂的，同一个词可能只以某一种写法出现：

```bash
grep -rl "郁洲" corpus/ | head -3
grep -rl "鬱洲" corpus/ | head -3
```

如果 opencc 没装，`variants()` 只返回原词，繁体写法就搜不到。装上它，或者手工 `--also`。

**最后确认这个词真的在二十四史里**。很多题目根本不在这个语料的覆盖范围内——比如 1651 年的人物，二十四史止于明史，压根没有。

---

## 症状：检索到一堆无关的东西

常见于单字或常用词。「州」「城」「守」这类会命中几万次。

**解法**：用更长的检索词，或者用官职名加地名的组合。检索词至少两个字，最好三个字以上。

也可能是**同名不同人/不同地**。「海州」在辽、唐、朝鲜都有，得靠上下文区分——这一步目前程序做不了，只能人工筛。

---

## 症状：模型返回空数组

`--debug` 显示 `模型返回 0 条`。

**可能原因**：

1. **这段真的没有人物。** 志、表类的文字大量是地理和制度描述，没有人名。这是正常的，不是 bug。
2. **分段太小**，上下文不足。调大 `chunks()` 的 n（在 `extract()` 里改，或者直接改 `chunks` 默认值）。
3. **分段太大**，模型漏抽。1400 字以上就有风险。

先看一眼那段文字长什么样：

```bash
python huijian.py search TERM --window 400 | head -30
```

---

## 症状：拦截率很高

```
攔下偽引 47 條
```

拦截本身是**功能不是故障**——说明校验在工作。但如果拦截数超过保留数，有问题。

**排查顺序**：

**一、繁简不匹配。** 这是最常见的原因。语料是简体，模型可能返回繁体引文，子串匹配就失败。

```bash
python huijian.py run TERM -o out/ --limit 2 --debug 2>&1 | grep 攔截
```

看被拦的引文，如果是繁体而语料是简体，就是这个问题。解法：在 `EXTRACT_PROMPT` 里加一句「evidence 必须与原文字形完全一致，包括繁简」。

**二、模型在改写。** 它把「二月，丁卯，虏寇寿阳」写成了「二月丁卯虏寇寿阳」（去了标点）。同样加强 prompt。

**三、模型在拼接。** 它把原文中不相邻的两段拼在一起。当前的子串匹配能拦住这种，因为拼接结果不是连续子串。**这正是校验的价值所在。**

**四、`chunks()` 切断了。** 模型引用的片段跨越了两个 chunk 的边界。调大分段可缓解。

---

## 症状：所有人都被标成「单方独载」

看一眼立场分布：

```bash
python huijian.py search TERM | grep "═══"
```

如果输出只有一个立场分组，说明**立场轴塌陷**——所有材料都来自同一方，独载检测失去意义。

这不是 bug，是材料问题。要么换题目，要么补另一方的语料（见 [02-使用手册](02-使用手册.md) 的「加自己的语料」）。

**典型例子**：1651 年广东的题目，唯一有记载的是清修《明史》，败方记述全在二十四史之外。这时候程序会给每个人都打上独载标记，全部无意义。

---

## 症状：事件对照一组都没有

```
事件對照 0 組
```

**按这个顺序查**：

**一、只有一个立场。** `align()` 默认 `cross_stance_only=True`，同立场内部不配对。

**二、纪年没换算成功。**

```bash
python duizhao.py eras 你的年号
```

返回「未收，不猜」就说明 `ERAS` 表里没有。加进去。

**三、阈值太高。**

```bash
python duizhao.py align findings.json -t 2
```

降到 2 试试。如果降到 2 才有结果，说明锚定信号很弱，这些配对多半是噪声。

**四、人物名不一致。** 事件层靠字符串相等匹配人名，「善明」和「刘善明」对不上。这是已知缺陷，暂时只能手工统一 findings.json 里的 person 字段。

---

## 症状：明显的误报

比如「除授 ↔ 罢黜」被报成硬矛盾——但一个人先升后贬是完全正常的。

**这条误报是故意留在代码里的**，让你第一次跑就理解「规则需要校准」。

删掉它：

```python
# duizhao.py 不涉及；改 huijian.py
PAIRS = [("战胜", "战败")]        # 删掉 ("除授", "罢黜")
```

更一般地：**看到误报就去改规则表**，这是预期的工作流，不是故障。所有规则都是待校准的假设。

---

## 症状：API 报错

```
! API 失敗: HTTP Error 401
```

| 错误码 | 含义 | 处理 |
|---|---|---|
| 401 | key 无效 | 检查 `echo $ANTHROPIC_API_KEY` |
| 429 | 频率超限 | 加 `--limit` 分批跑，或在 `extract()` 里加 `time.sleep` |
| 400 | 请求格式错 | 多半是 chunk 太长，调小分段 |
| 529 | 服务过载 | 等一会儿重跑 |

**没有自动重试**是有意设计。失败会打印并跳过那一段，不会静默吞掉。

---

## 症状：花钱超预期

**永远先 `--dry-run`。** 它会列出每一次将要发出的请求和字数。

数一下行数就是调用次数。文言文大致一字一 token。

日常防护：

```bash
python huijian.py run TERM -o out/ --limit 20
```

`--limit` 到了就停，已抽的结果照常分析输出。

## 怎么检查中间状态

程序没有中间文件，但可以在 Python 里直接调：

```python
import huijian as H

# 看检索命中
hits = H.scan(H.variants('郁洲', ['郁州']))
print(len(hits))
for h in hits[:3]:
    print(h[0], h[1], h[2])
    print(h[4][:100])

# 看分段
print([len(c) for c in H.chunks(hits[0][4])])

# 单独测确定性层，不调 API
rows = [{'person':'张稷','acts':['被杀'],'time':'延昌二年',
         'evidence':'...','book':'魏书','juan':'卷八','stance':'北朝系'}]
H.report(H.analyse(rows, ['南朝系','北朝系']), 0)
```

事件层同理：

```python
import duizhao as D
print(D.to_year('延昌二年'))
print(D.lex_tags('虏寇寿阳'))
```

## 什么不算 bug

- **返回「未见著录」** — 这是功能。无据时应该空，不该编。
- **拦截了伪引** — 校验在工作。
- **结果比预期少** — 说明规则保守。宁可漏，不可错。
- **同一事件重复出现在不同卷** — 纪、传、志本来就会重复记同一事，这正是互见的基础。
